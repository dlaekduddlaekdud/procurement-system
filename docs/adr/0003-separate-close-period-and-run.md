# ADR 0003: 마감 상태와 실행 이력을 분리한다

- 상태: 수락
- 결정일: 2026-09-03

## 배경

월 마감은 특정 기간이 현재 열려 있는지 닫혀 있는지를 나타내는 업무 상태이면서, 동시에 수동·자동 실행, 성공·실패, 중복 요청, 재시도를 추적해야 하는 작업이다.

기간 상태와 마지막 실행 결과만 한 행에 저장하면 실패 후 재실행할 때 이전 실패 정보가 사라진다. 반대로 실행 로그만 두고 기간 상태를 매번 추론하면 입고 같은 다른 업무가 마감 여부를 확인할 때 실행 이력 전체를 해석해야 한다.

## 결정

마감의 현재 상태와 실행 이력을 별도 테이블로 관리한다.

```text
CLOSE_PERIOD 1 ─── N CLOSE_RUN

close_period: period(UNIQUE), OPEN/CLOSED, closed_at, version
close_run:    attempt_no, RUNNING/SUCCESS/FAILED/SKIPPED,
              trigger_type, started_at, completed_at, failure_message, requested_by
```

- `close_period`는 기간별 한 행으로 현재 업무 상태를 표현한다.
- `close_run`은 마감 호출마다 새 행을 만들고, 같은 기간에서 `attempt_no`를 1씩 증가시킨다.
- 마감이 성공하면 실행을 `SUCCESS`로 완료하고 기간을 `CLOSED`로 전이한다.
- 이미 닫힌 기간에 대한 호출은 집계 결과를 변경하지 않고 새 실행을 `SKIPPED`로 기록한다.
- 집계가 실패하면 별도 트랜잭션에서 `FAILED` 실행과 실패 사유를 남기고 기간은 `OPEN`으로 유지한다.
- 실패한 기간은 새 attempt로 다시 실행할 수 있으며, 완료된 과거 실행 행을 재사용하거나 덮어쓰지 않는다.
- 마감 스냅샷은 `close_run_id`에 연결해 어느 실행의 결과인지 추적한다.
- `trigger_type`이 `MANUAL`이면 `requested_by`를 필수로, `SCHEDULED`이면 `NULL`로 강제한다. 실행 주체의 무결성은 애플리케이션이 아니라 DB CHECK 제약으로 보장한다.

### 동시 요청의 잠금 범위

마감 실행과 마감 여부 확인은 같은 `close_period` 행을 보지만 필요한 잠금이 다르므로 분리한다.

- **마감 실행**은 기간 행을 배타 잠금한 뒤 attempt를 부여해 상태 확인과 실행 생성을 직렬화한다.
- 기간 행이 아직 없는 최초 동시 요청은 잠글 대상이 없으므로, `period` 고유키에 `insert ignore`로 행을 먼저 확보한 뒤 잠근다. 행이 없는 상태의 동시 요청은 이 삽입 자체가 직렬화 지점이 된다.
- 등록과 잠금은 **호출자와 같은 트랜잭션**에서 수행한다. 등록만 별도 트랜잭션으로 분리하면, 호출자가 이미 배타 잠금을 잡고 있는 기간을 다시 마감할 때 등록이 호출자의 잠금을 기다리다 잠금 대기 시간을 초과한다.
- **마감 여부 확인**(입고·송장 등록)은 읽기 검증이므로 기간 행을 만들지 않고 공유 잠금으로만 읽는다. 행이 없으면 해당 기간을 한 번도 마감하지 않았다는 뜻이므로 열린 기간으로 판단한다. 배타 잠금으로 올리지 않으므로 동시 등록끼리는 교착이 발생하지 않고, 진행 중인 마감과는 배타 잠금으로 배제된다.

## 고려한 대안

### 대안 1: 기간 행에 마지막 실행 정보까지 저장

테이블은 하나로 줄지만 재실행할 때 이전 성공·실패·요청자 정보가 덮어써진다. 실패 원인과 재시도 과정을 감사할 수 없으므로 선택하지 않았다.

### 대안 2: 실행 이력만 저장하고 기간 상태를 실행 결과에서 계산

상태 중복은 피할 수 있지만 모든 쓰기 작업이 최신 실행을 조회하고 해석해야 한다. 진행 중·실패·중복 실행이 섞이면 현재 마감 여부를 판단하는 규칙도 복잡해지므로 선택하지 않았다.

### 대안 3: 이미 닫힌 기간의 재실행 요청을 기록하지 않고 반환

결과 데이터는 바뀌지 않지만 누가 언제 중복 실행을 요청했는지 알 수 없다. 멱등성을 결과 불변과 요청 이력 보존으로 함께 설명하기 위해 `SKIPPED` 실행을 남긴다.

### 대안 4: 실패한 실행 행을 초기화해 재사용

행 수는 줄지만 실패 증거와 시도 순서가 사라진다. 재시도를 새로운 attempt로 기록해 실행별 원인과 결과를 보존한다.

### 대안 5: 마감 여부 확인에서도 기간 행을 만들고 배타 잠금

마감 실행과 같은 경로를 재사용할 수 있어 코드는 줄지만, 입고와 송장 등록마다 해당 월의 기간 행에 배타 잠금이 걸린다. 같은 달의 모든 등록이 행 하나에서 직렬화되고, 등록 시 발생하는 공유 잠금과 배타 잠금 승격이 겹쳐 교착까지 발생한다. 마감 여부는 읽기 검증이므로 공유 잠금으로 충분하다.

### 대안 6: 기간 행 등록만 별도 트랜잭션으로 분리

`insert ignore`가 중복 키를 만나면 기존 행에 공유 잠금을 잡으므로, 잠금 보유 구간을 좁히려면 등록을 먼저 커밋하는 방법을 생각할 수 있다. 그러나 등록이 다른 커넥션에서 실행되면 호출자가 이미 배타 잠금을 잡고 있는 기간을 다시 마감할 때 자기 자신의 잠금을 기다리게 되어 잠금 대기 시간을 초과한다. 실제로 이 방식은 이미 마감된 기간의 재실행 경로에서 `LockTimeoutException`을 일으켜 철회했다.

## 결과

- 업무 로직은 `close_period`만 조회해 마감 여부를 명확하게 판단할 수 있다.
- 성공, 중복 실행, 실패, 재실행의 순서를 `close_run`으로 설명할 수 있다.
- 동일 기간을 다시 호출해도 성공 스냅샷과 기간 상태가 변하지 않는다.
- 마감 여부 확인이 기간 행을 만들지 않으므로, 한 번도 마감하지 않은 기간에는 `close_period` 행이 존재하지 않는다. 기간 목록을 조회하는 기능은 이 점을 전제해야 한다.
- 상태 테이블과 이력 테이블을 함께 관리하는 복잡도를 감수한다. 실패 이력은 별도 트랜잭션으로 보존하되, 기간 행 등록과 배타 잠금은 마감 호출자와 같은 트랜잭션에서 수행한다.
- `attempt_no`의 유일성과 잠금 범위 분리 정책을 유지해야 한다. 마감 여부 확인이 배타 잠금을 잡도록 되돌리면 교착이 다시 발생한다.
- 이미 존재하는 기간 행에 대해 마감 요청 두 건이 정확히 겹치면, 두 요청이 각각 `insert ignore`로 얻은 공유 잠금을 배타 잠금으로 올리는 과정에서 교착이 발생할 수 있다. 현재는 마감 실행 빈도가 낮아 감수하며, 해소하려면 `insert ignore` 대신 잠금을 잡지 않는 선등록 경로가 필요하다.

## 검증 결과

- `CloseServiceTest`에서 최초 성공 후 기간이 `CLOSED`가 되고, 중복 실행은 결과를 바꾸지 않은 채 `SKIPPED` attempt를 추가하는지 검증했다.
- `CloseServiceTest`에서 집계 실패 시 기간이 `OPEN`으로 유지되고 `FAILED`가 기록되며, 재실행 시 attempt가 증가하고 `SUCCESS`로 종료되는지 검증했다.
- `CloseSnapshotServiceTest`에서 실패한 실행의 스냅샷이 롤백되고 재실행 성공 시 한 벌만 생성되는지 검증했다.
- `ClosePeriodApiTest`에서 ADMIN 수동 마감 결과가 기간 상태와 실행 이력에 함께 반영되는지 검증했다.
- `CloseConcurrencyTest`에서 기간 행이 없는 동일 기간의 최초 동시 마감 요청에도 성공 결과가 한 벌만 생성되는지 검증했다.
- `GoodsReceiptServiceTest.allowsOnlyOneConcurrentReceiptForLastRemainingQuantity`에서 동시 입고 등록이 마감 기간 확인 단계에서 교착 없이 처리되는지 검증했다.
